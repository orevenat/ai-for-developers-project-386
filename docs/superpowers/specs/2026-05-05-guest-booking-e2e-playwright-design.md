# Дизайн-спецификация: E2E тест гостевого бронирования (Playwright)

Дата: 2026-05-05

## Цели
- Добавить интеграционный E2E тест, покрывающий полный гостевой путь бронирования через фронтенд и бэкенд.
- Автоматически поднимать frontend и backend для теста.
- Перед тестом очищать тестовую базу и наполнять ее через админский UI.
- Сделать тест устойчивым к колебаниям конкретных дат, опираясь на выбор первого доступного слота.

## Объем работ
### Включено
- Один E2E тест Playwright для гостевого потока:
  1) `/` → 2) `/book` → 3) выбор 15-минутного события → 4) выбор дня → 5) выбор слота → 6) ввод ФИО и email → 7) подтверждение и успех.
- Подготовка данных: очистка тестовой БД и создание event types (15 и 30 минут) через админский UI.
- Запуск двух webServer: Rails backend и Vite frontend.

### Вне объема
- Админский поток кроме подготовки данных.
- Изменение API.

## Предпосылки и допущения
- Тесты запускаются с `RAILS_ENV=test` и используют тестовую БД.
- Frontend доступен на `http://localhost:5173`.
- Backend доступен на `http://localhost:3000`.

## Подходы
1) Playwright + подготовка данных перед тестом (рекомендовано).
2) Playwright + webServer для фронта и бэка, тест на готовых данных.
3) Моки API (быстро, но не сквозной тест).

## Архитектура теста
- Размещение Playwright-конфигурации в корне репозитория.
- `webServer` поднимает два процесса:
  - Backend: `RAILS_ENV=test mise exec -- bundle exec rails s -p 3000`.
  - Frontend: `VITE_API_BASE_URL=http://localhost:3000 npm --prefix frontend run dev -- --host --port 5173`.
- Перед запуском тестов выполняется подготовка данных:
  - очистка тестовой БД через `RAILS_ENV=test bin/rails db:reset`.
  - создание event types на 15 и 30 минут через админский UI.
- Подготовка данных выполняется в `globalSetup` Playwright через админские страницы.
- Тесты размещены в `tests/e2e/` или `playwright/tests/` (окончательный путь фиксируется в реализации).

## Сценарий E2E
### Подготовка данных
1) Очистить тестовую БД (`RAILS_ENV=test bin/rails db:reset`).
2) Создать event types через админский UI:
   - 15 минут (используется в тесте).
   - 30 минут (для покрытия параллельного варианта).

### Гостевой поток
1) Открыть `/` и перейти на страницу бронирования (по CTA/ссылке).
2) На `/book` найти карточку события с длительностью 15 минут и открыть ее.
3) На `/book/:eventTypeId` выбрать доступный день.
4) Выбрать первый свободный слот.
5) Перейти на `/book/:eventTypeId/confirm`.
6) Ввести ФИО и email.
7) Подтвердить и увидеть экран успеха.

## Стратегия селекторов
- Предпочтительно использовать роль и видимый текст.
- Если в UI нет надежных текстовых маркеров, добавить `data-testid` только в реализации (не на этапе дизайна).

## Ожидания и устойчивость
- Явно ждать появления данных (карточек событий, слотов, формы подтверждения).
- Не закреплять даты жестко: выбирать первую доступную дату/слот в UI.
- Проверять успех через заголовок/текст успеха.
- Подготовка данных должна завершаться до старта теста.

## Критерии готовности
- Тест проходит локально с поднятыми webServer.
- Покрыт весь гостевой путь от главной до успеха бронирования.
- Нет хрупких ожиданий по конкретным датам/временам.
